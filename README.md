# Бронювання переговорних кімнат — UA-Skills Hackathon

Веб-застосунок для бронювання переговорних кімнат в офісі.

**Стек:** Next.js 14+ (App Router, TypeScript) · Prisma ORM · PostgreSQL · Tailwind CSS · Lucide React

## Швидкий старт (Docker)

Найпростіший спосіб — підняти все однією командою. Потрібен лише встановлений Docker і Docker Compose.

```bash
docker-compose up --build
```

Після завершення білда застосунок буде доступний на **http://localhost:3000**.

Під час старту контейнер автоматично:
1. піднімає PostgreSQL і чекає на її готовність;
2. синхронізує схему БД (`prisma db push`);
3. заповнює базу тестовими даними (`prisma db seed`) — **виконується при кожному запуску**, тож база завжди повертається у "чистий" демо-стан.

Щоб зупинити й прибрати контейнери разом з даними БД:

```bash
docker-compose down -v
```

За скільки хвилин до кінця бронювання показувати тост-сповіщення (див. [Сповіщення про кінець бронювання](#5-сповіщення-про-кінець-бронювання)) — керується змінною `NOTIFY_BEFORE_MINUTES` (дефолт `10`). Щоб змінити без редагування `docker-compose.yml`, створи `.env` у корені проєкту з рядком `NOTIFY_BEFORE_MINUTES=5` — Docker Compose підхопить його автоматично.

## Тестування

### Юніт-тести

```bash
npm run test        # один прогін (Vitest)
npm run test:watch  # у режимі спостереження
```

Юніт-тести (`lib/booking-validation.test.ts`) покривають перевірку перетинів бронювань (впритул, часткове перекриття, повний збіг, сусідні дні) і коректність щотижневих повторень через перехід DST (`addWeeksInKyiv`). Працюють без БД і без запущеного сервера.

### Інтеграційні тести (Supertest)

```bash
npm run test:integration
```

Ця одна команда сама:
1. піднімає **справжній** dev-сервер Next.js на порту `3100` (окремий від звичайного `3000`, щоб не конфліктувати зі звичайним `npm run dev` чи запущеним Docker-контейнером);
2. чекає, поки `GET /api/config` почне відповідати;
3. ганяє сьют `tests/integration/bookings.integration.test.ts` через **Supertest** — реальні HTTP-запити до цього сервера;
4. гасить сервер після завершення (успішного чи ні).

Сценарії, які покриті:
- **Успішне створення** бронювання (і перевірка, що запис реально з'явився в БД, а не лише в JSON-відповіді).
- **Успішне скасування** свого бронювання автором (+ що повторне скасування вже неіснуючого повертає `404`).
- **Відмови валідації**: час у минулому, час поза робочими годинами (09:00–19:00 за Києвом), перетин з існуючим бронюванням, запит без автентифікації (`401`).
- Регресійний кейс "впритул одразу після існуючого — дозволено" (той самий баг, що фіксили раніше в `POST /api/bookings`, тепер підтверджений і на рівні HTTP, а не лише юніт-тестом).

**Передумови:**
- `DATABASE_URL` у `.env` в корені проєкту повинен вказувати на БД, до якої матиме доступ і тестовий процес, і сервер, що його піднімає `start-server-and-test` — простіше кажучи, просто скопіюй `.env.example` в `.env`, як для звичайного [локального запуску без Docker](#локальний-запуск-без-docker).
- Тести навмисно піднімають сервер саме через `next dev` (а не проти вже запущеного Docker-контейнера в продакшн-режимі) — у `NODE_ENV=production` сесійна кука видається з прапорцем `Secure`, який блокує її повторну відправку по звичайному `http://` (не `https://`), а Supertest-агент саме так і працює. У dev-режимі цієї проблеми немає.
- Тести створюють ізольовану тестову кімнату (`__INTEGRATION_TEST_ROOM__`) і тестового користувача (унікальний email на кожен запуск) та прибирають їх за собою в `afterAll` — не займаний і не змінюють демо-дані сіда.

## Як влаштована перевірка перетинів бронювань

Два інтервали `[startA, endA)` і `[startB, endB)` вважаються **такими, що перетинаються**, якщо виконується умова зі строгими нерівностями:

```ts
startA < endB && startB < endA
```

Через строгі `<` (а не `<=`) бронювання **впритул** (наприклад, 10:00–11:00 і 11:00–12:00) коректно НЕ вважаються конфліктом — момент 11:00 є кінцем одного слота й одночасно початком іншого, і жодна кімната фактично не зайнята двома людьми одночасно.

На сервері (`POST /api/bookings`) ця перевірка виконується у два етапи:
1. **Груба фільтрація на рівні SQL** — вибираються лише бронювання тієї ж кімнати, які потенційно можуть перетинатись (`startTime < newEnd AND endTime > newStart`), з використанням індексу `[roomId, startTime, endTime]`.
2. **Точна перевірка в коді** — з відібраних кандидатів шукається реальний конфлікт за формулою вище.

## Захист від race condition

Два користувачі можуть одночасно натиснути "Забронювати" на той самий (або пересічний) слот. Без додаткового захисту обидва запити встигли б прочитати "кімната вільна" ще до того, як хтось із них закомітив свій запис — і кімната виявилась би подвійно забронированою. `POST /api/bookings` захищається одразу двома незалежними механізмами:

1. **Пессимістичний DB-лок.** Усередині Prisma-транзакції спершу виконується `SELECT id FROM rooms WHERE id = $roomId FOR UPDATE` — це блокує рядок кімнати в PostgreSQL на час транзакції. Другий конкурентний запит на ту саму кімнату не отримує "застарілий" знімок даних — він просто **чекає** на звільнення локу, і лише після цього читає вже актуальний (щойно оновлений) список бронювань.
2. **Ізоляція SERIALIZABLE.** Транзакція додатково виконується з `isolationLevel: Serializable` — найсуворішим рівнем ізоляції PostgreSQL. Якщо, попри лок, СУБД усе ж виявить конфлікт читання/запису (serialization failure, код `40001`), вона сама відхилить одну з транзакцій, а наш код (`runWithSerializationRetry`) перехоплює цю помилку (Prisma-код `P2034`) і повторює спробу до 3 разів із невеликим випадковим бекофом.

Разом це дає гарантію: два конкурентні запити на той самий слот ніколи не створять дублікат — один із них завжди або чекає на лок і бачить уже зайнятий слот, або отримує serialization failure й при повторній спробі бачить актуальний стан.

## Чому час зберігається в UTC

Усі дати (`Booking.startTime`, `Booking.endTime`) зберігаються в базі **виключно в UTC** — це стандартна практика для будь-якого застосунку з часовими поясами, і ось чому:

- **Однозначність.** UTC-мітка часу — це завжди один і той самий фізичний момент, незалежно від того, хто й де на неї дивиться. Зберігання "локального" часу без прив'язки до конкретного поясу створило б неоднозначність під час переходу на літній/зимній час.
- **Конвертація тільки на межах системи.** Робочі години офісу (09:00–19:00) визначені саме за `Europe/Kyiv`, тому конвертація Kyiv ⇄ UTC відбувається лише у двох місцях:
  - на сервері, при валідації вхідних даних (`lib/booking-validation.ts`, через `date-fns-tz`) — щоб перевірити, чи бронювання вкладається в робочі години за Києвом;
  - на клієнті, при відображенні (`lib/schedule-utils.ts`) — де час рядків сітки форматується вже під часовий пояс браузера користувача, а дати колонок (дні тижня) — навпаки, завжди залишаються прив'язаними до `Europe/Kyiv`, бо це офісний, а не "чий завгодно локальний" календар.
- **Зручність порівняння.** Оскільки в базі — чисті UTC-миттєвості, перевірку перетинів (`startA < endB && startB < endA`) можна робити прямим порівнянням `Date`/`timestamp`, без жодної логіки часових поясів — вона там просто не потрібна.

## Бонусні фічі

### 1. Підтвердження email (dev-режим)

Акаунт після реєстрації створюється з `isVerified: false`. Одразу після створення сервер генерує одноразовий токен (модель `VerificationToken`, TTL 24 години) і **виводить посилання підтвердження в консоль сервера** — реальний SMTP не потрібен:

```
📧 [DEV] Лист підтвердження для user@example.com:
   Перейдіть за посиланням, щоб підтвердити email:
   http://localhost:3000/api/auth/verify?token=...
```

Перехід за цим посиланням (`GET /api/auth/verify`) позначає користувача підтвердженим і видаляє токен (одноразовий). Доки email не підтверджено, `POST /api/bookings` свідомо відхиляє спробу створити бронювання (`403`, свіжа перевірка `isVerified` з БД — не з JWT-сесії, бо статус міг змінитися вже після видачі токена). У застосунку неверифікований користувач бачить попередження над сіткою й діалог з кнопкою "Надіслати ще раз" (`POST /api/auth/resend-verification`) замість форми бронювання.

### 3. Повторювані щотижневі бронювання

У формі створення бронювання є чекбокс "Повторювати щотижня" + кількість повторень (2–52). Усі бронювання серії отримують спільний `Booking.seriesId` (nullable — для одноразових бронювань лишається `null`). Ключові деталі реалізації:

- **Дати повторень рахуються через Kyiv-годинник, а не raw-мілісекунди** (`addWeeksInKyiv` у `lib/booking-validation.ts`): якщо просто додати `N × 7 × 24` години в UTC, перехід на літній/зимній час усередині серії зсунув би фактичний Kyiv-час зустрічі на годину. Через `toZonedTime`/`fromZonedTime` кожне повторення завжди залишається, наприклад, рівно "щовівторка о 10:00 за Києвом" — це покрито регресійним тестом на реальному переході DST 2026-10-25.
- **Створення серії атомарне (all-or-nothing).** Усі occurrences перевіряються й створюються в ОДНІЙ транзакції з тим самим room-локом, що й одноразові бронювання. Якщо конфліктує хоча б одне повторення — відкочується вся серія, жодного "часткового" бронювання не залишається.
- **Скасування:** окремо одного бронювання (`DELETE /api/bookings/:id`, як і раніше) або всієї серії одразу (`DELETE /api/bookings/series/:seriesId`) — останній видаляє лише **майбутні** повторення користувача, минулі лишаються в історії "Моїх бронювань".

### 4. Фільтр кімнат за місткістю

Над сіткою розкладу — рядок пілюль "Місткість: Будь-яка / 2+ / 4+ / 6+ / ...", згенерований динамічно з реальних `capacity` завантажених кімнат (а не захардкоджений список чисел). Фільтрує лише клієнтський список видимих кімнат (`rooms.filter(r => r.capacity >= minCapacity)`) — без додаткових запитів до сервера. Якщо активна кімната випадає з нового фільтра, застосунок автоматично перемикається на першу відповідну.

### 5. Сповіщення про кінець бронювання

`BookingCalendar` кожні 15 секунд перевіряє вже завантажені бронювання поточної кімнати/тижня: якщо (а) бронювання належить поточному користувачу, (б) до його кінця лишилось ≤ `NOTIFY_BEFORE_MINUTES` хвилин (дефолт 10, читається з env через `GET /api/config` — runtime-змінна, а не `NEXT_PUBLIC_*`, щоб її можна було міняти в `docker-compose.yml` без перезбірки образу) і (в) одразу після нього в тій самій кімнаті вже починається інше бронювання (впритул, без розриву) — показується тост із дзвіночком. Перевірка йде на "живому" стані `bookings`, тому якщо власне бронювання АБО те, що йде одразу за ним, скасовується до спрацювання — умова просто перестає виконуватись і сповіщення не приходить (жодної окремої логіки скасування таймера не потрібно).

### 6. Мобільна адаптація сітки розкладу

Сітка (7 днів × 20 слотів) залишається читабельною на вузьких екранах через горизонтальний скрол внутрішнього контейнера (`overflow-x-auto`) із текстовою підказкою та градієнт-хінтом справа — самі елементи керування (кімнати, фільтр місткості, навігація по тижнях, підпис часових поясів) стають вертикальним стеком на `< sm` замість горизонтального ряду.

## Авторизація та захист дій

- Header (`components/Header.tsx`) показує "Вхід"/"Реєстрація" для гостя і ім'я користувача + "Вийти" для авторизованого — стан бере зі спільного `AuthProvider` (`lib/auth-context.tsx`), який один раз опитує `GET /api/auth/me` і роздає результат усім компонентам (Header, календар, "Мої бронювання").
- Клік по вільному слоту в неавторизованому стані показує `LoginRequiredDialog` замість форми бронювання, з кнопкою переходу на `/login` — сервер (`POST /api/bookings`) все одно незалежно перевіряє сесію, тож клієнтська перевірка лише покращує UX, а не замінює захист.
- `/my-bookings` перенаправляє неавторизованого користувача на `/login` і показує список власних бронювань (`GET /api/bookings?mine=true`), розділений на майбутні (зі скасуванням) і минулі (лише перегляд).
